## 1. One-sentence pitch

HaqCheck tells an Indian gig worker which welfare entitlement they qualify for, and the answer is computed by **Cedar** (via **Amazon Verified Permissions**) from a versioned, human-readable rulebook, so every answer is a **citation to a specific rule**, never an LLM's guess.

*Haq* = right / entitlement. The demo line: **"Appeal a citation, not a vibe."**

## 2. Problem

- India's Social Security (Central) Rules, 2026 set a work-days threshold (reported as 90 days) for gig workers' social-security eligibility, tied to e-Shram registration.
- Karnataka's High Court (July 2026) ordered platforms (Swiggy, Zomato, Zepto, Urban Company) to pay a per-ride welfare cess into a state fund, with the rate varying by vehicle type.
- The Centre and Karnataka are in an active conflict over which rules bind. A delivery worker cannot tell: am I over the threshold, which fund covers me, which rule applies in my state.
- Existing tools (MyScheme, india.gov.in) are directories. Nothing *verifies* a person against a rule and shows its work.
- The most common hackathon submission will be "upload a document, Bedrock summarizes it." HaqCheck is the opposite: the LLM is not allowed to decide anything.

> **Fact-verification requirement (pre-event, allowed as "learning"):** the rule figures above come from news coverage. Before Sept 17 the team must read the primary sources (the Central Rules 2026 text; the Karnataka HC order) and record the exact clause references. The shipped policies encode what the primary sources say, not what the press said. If a primary source cannot be obtained, that rule ships with an explicit `@confidence("secondary-source")` annotation shown in the UI.

## 3. Goals and non-goals

**Goals (must ship by Sunday Sept 20):**
1. A worker answers a short form (5–7 fields) and gets, per benefit, a decision of **Eligible / Not eligible / Not applicable** (card wording is exactly these three labels; the citation line underneath says why), plus the exact rule(s) that determined it, quoted with source.
2. A **jurisdiction toggle** (Central / Karnataka) that re-evaluates the same facts and visibly changes the result and the cited rules.
3. A **plain-language explanation** of the result and the next step (which fund, which form), in English and Hindi (Kannada if time), generated by Bedrock **from the decision and the cited rule text only**.
4. A live URL on AWS, with a cost story: everything scales to zero.
5. A rehearsed 3-minute demo with **two** worked cases, not one.

**Non-goals (explicitly cut by the council; do not build):**
- Screenshot/OCR extraction of earnings from platform apps. Form input is primary, not a fallback.
- Bedrock AgentCore Policy gating of the agent's tools.
- Login/accounts (Cognito). Cases are anonymous.
- File uploads (S3). Nothing is uploaded.
- More than two jurisdictions or more than two benefit types.
- Auto-applying LLM-generated policy. See §7 for the stretch that is allowed.

## 4. Users

- **Primary (the demo persona):** a Bengaluru delivery rider on a two-wheeler, working across two platforms, ~73 days in the last 12 months, registered on e-Shram.
- **Secondary:** a volunteer at a gig-workers' union or NGO helping several workers check status; benefits from the citation output because it is what they'd quote back to a platform or a labour office.
- **Judge:** non-lawyer, sees 3 minutes. Must be able to see the difference between "an LLM said so" and "this rule, this clause, evaluated by a policy engine" without understanding Cedar.

## 5. Architecture (Ship It)

```
Browser (React/Vite, Amplify Hosting)
   │  1. POST /evaluate  {facts, jurisdiction}
   │  2. POST /explain   {results, language}      (after cards render)
   ▼
API Gateway (HTTP API)
   ├─► Lambda "evaluate" (Python 3.12, boto3)
   │     ├─► Amazon Verified Permissions: IsAuthorized per covered benefit
   │     │      returns decision + determiningPolicies (AVP policy IDs)
   │     ├─► join AVP policy IDs → {@id, @source, @confidence} via policy map
   │     └─► DynamoDB: write case (facts, decisions, cited policies, ruleset version)
   └─► Lambda "explain" (Python 3.12, Strands Agents SDK → Bedrock)
           explain(decision, cited rule text, language) → plain-language text
           returned when ready (no streaming; HTTP API cannot stream Lambda responses)

Browser renders decision cards from /evaluate immediately; the explanation fills in later.
```

**Why each service is load-bearing (this is the "Built on AWS" answer):**

| Service | Role | Why it is not decoration |
|---|---|---|
| **Amazon Verified Permissions (Cedar)** | The decision engine. Policies live in an AVP policy store; `IsAuthorized` returns `decision` and `determiningPolicies`. | The core claim of the project. Remove it and there is no product. |
| **Lambda + API Gateway** | Stateless evaluate endpoint. | Scales to zero; cost story for the demo. |
| **DynamoDB** | Case log keyed by case id; ruleset version stamped on each case. | Lets the demo show "same facts, ruleset v2, different result", and gives the NGO persona a record. |
| **Bedrock (via Strands Agents SDK)** | Explanation only, and (stretch) rule-drafting assistant. | Grounded on the engine's output; never decides. The demo says this out loud. |
| **Amplify Hosting** | Static frontend with a public URL. | Ship It requirement. |

Policies are **authored in the repo** as `.cedar` files with a Cedar schema, and pushed to AVP by a sync script. Git is the source of truth; AVP is the runtime. This keeps the rulebook reviewable as a diff.

## 6. Data model

### 6.1 Cedar schema (namespace `HaqCheck`)

- **Entity `Worker`** (principal). Attributes:
  - `state: String` (ISO-ish code, e.g. `"KA"`, `"MH"`)
  - `daysWorkedLast12m: Long`
  - `eshramRegistered: Bool`
  - `platforms: Set<String>` (e.g. `["zomato","swiggy"]`)
  - `vehicle: String` (`"bicycle" | "two_wheeler" | "three_wheeler" | "four_wheeler" | "none"`). Collected because the Karnataka cess *rate* depends on it; not used by any eligibility policy unless the primary source makes it a condition. Shown on the card as context only.
  - `age: Long` (validation only: 18–80; no policy uses it).
- **Entity `Benefit`** (resource). Two instances: `Benefit::"central_social_security"`, `Benefit::"ka_welfare_fund"`. Attribute: `name: String`. Jurisdiction is not an attribute; it is the choice of policy store.
- **Action `claim`**: `principal: Worker`, `resource: Benefit`. No context attributes: the jurisdiction is selected by choosing the policy store, not by a context value.
- **No entities are stored in AVP.** Each request passes the `Worker` and `Benefit` entities inline to `IsAuthorized` (principal id = the case id). There is no entity management to build.

### 6.2 Policies (illustrative shape; exact thresholds must be replaced with primary-source values)

```cedar
@id("IN-SSR2026-90day")
@source("Social Security (Central) Rules 2026, rule <N>: minimum <90> days of work in the preceding 12 months")
@confidence("primary")
permit(
  principal,
  action == Action::"claim",
  resource == Benefit::"central_social_security"
) when {
  principal.eshramRegistered &&
  principal.daysWorkedLast12m >= 90
};

@id("KA-HC-2026-cess-scope")
@source("Karnataka HC order, <case no.>, 4 Jul 2026, para <N>: workers on notified platforms in Karnataka")
@confidence("primary")
permit(
  principal,
  action == Action::"claim",
  resource == Benefit::"ka_welfare_fund"
) when {
  principal.state == "KA" &&
  principal.platforms.containsAny(["zomato","swiggy","zepto","urban_company"])
};

@id("KA-HC-2026-out-of-state")
@source("Same order: fund is Karnataka-specific")
@confidence("primary")
// Logically redundant with the permit's state check, kept on purpose:
// a firing forbid appears in determiningPolicies, which is how the
// engine (not the UI) says "Not applicable" with a citation.
forbid(
  principal,
  action == Action::"claim",
  resource == Benefit::"ka_welfare_fund"
) unless { principal.state == "KA" };
```

Design rules for policies:
- Every policy carries `@id`, `@source`, `@confidence`. The UI renders these; they are the citation.
- **Two rulebooks, two AVP policy stores, one shared schema.** The `central` rulebook is `policies/common/*.cedar`. The `karnataka` rulebook is a **superset**: `policies/common/*.cedar` plus `policies/karnataka/*.cedar` (the KA overlay). The sync script pushes `common` to both stores and the overlay only to the `karnataka` store. The rulebook drawer shows `common` and the overlay side by side with the overlay highlighted. Toggling jurisdiction switches the store id.
- **Rulebook manifest.** Each rulebook has a `manifest.json` listing the benefits it covers: `central` → `[central_social_security]`; `karnataka` → `[central_social_security, ka_welfare_fund]`. The Lambda consults it before calling AVP.
- **Verdict mapping (three values from a two-valued engine):**
  1. Benefit not in the active rulebook's manifest → **Not applicable**, citation line "not covered by the <name> rulebook". No AVP call.
  2. AVP `ALLOW` → **Eligible**, citing the permit(s) in `determiningPolicies`.
  3. AVP `DENY` with a `forbid` in `determiningPolicies` → **Not applicable**, citing that forbid (e.g. out-of-state).
  4. AVP `DENY` with empty `determiningPolicies` (no permit matched) → **Not eligible**. AVP gives no citation here, so the "why" list comes from `requirements.json`: a hand-written mirror of each permit's conditions with human labels, evaluated client-side to show met / not met (e.g. "73 of 90 days").
- **Policy ID mapping (critical).** `IsAuthorized` returns `determiningPolicies` as AVP-assigned opaque `policyId`s, not the Cedar `@id`. `sync_policies.py` therefore records, per store, `avpPolicyId → {id, source, confidence, file}` into `policy_map.json` at sync time. The map is written onto the `RULESET#` DynamoDB item and also bundled with the Lambda as a fallback.
- **Sync strategy.** The two policy stores are created **once** and their ids are stable for the whole event. Each sync deletes and recreates the *policies* inside a store (which changes policy ids), regenerates the map, and writes a new `RULESET#` version + moves `CURRENT`. The store id in `RULESET#` therefore never rotates in practice; the Lambda's cache-drop path exists only for the policy map.

### 6.3 DynamoDB

Table `haqcheck` (on-demand), single-table:
- `PK = CASE#<ulid>`, `SK = v1`: `facts` (map), `jurisdiction`, `rulesetVersion`, `results` (list of `{benefitId, verdict, avpPolicyIds[], cited[]}`; both id forms are stored because AVP ids become meaningless after a resync while `cited[].id` stays readable), `createdAt`. TTL 30 days.
- `PK = RULESET#<jurisdiction>`, `SK = <version>`: `policyStoreId`, `gitSha`, `publishedAt`, `manifest` (list of covered benefit ids), `policyMap` (map of AVP policyId → citation metadata). Plus `SK = CURRENT` pointing at the active version.

### 6.4 Repo layout (created on Sept 17, not before)

```
haqcheck/
  policies/
    schema.cedarschema        # shared by both stores
    common/*.cedar            # central rulebook; pushed to BOTH stores
    karnataka/*.cedar         # KA overlay; pushed to the karnataka store only
    rulebooks/central.manifest.json, karnataka.manifest.json
    requirements.json         # human-readable mirror of each permit's conditions + nextStep text
    tests/cases.json          # table of {facts, jurisdiction, expected verdict + cited @ids}
  backend/                    # Python 3.12, SAM template
    evaluate/handler.py       # manifest check, AVP calls, policy-map join, DynamoDB write
    explain/handler.py        # Strands agent, Bedrock, grounded prompt
    scripts/sync_policies.py  # push schema + .cedar to AVP stores, emit policy_map.json, write RULESET# item
    scripts/run_tests.py      # runs cases.json against AVP; also ListPolicies count check per store
  frontend/                   # React + Vite, Amplify Hosting
  README.md                   # includes AI-tools disclosure (rule 03)
```

## 7. Components

### 7.1 `evaluate` Lambda
- Input: `{facts: Worker attrs, jurisdiction: "central" | "karnataka"}`. Validate types and ranges (days 0–366, age 18–80, state in list).
- Read the `RULESET#<jurisdiction>` / `CURRENT` item (store id, manifest, policy map); cache in Lambda memory. On an AVP `ResourceNotFoundException` or an unknown policy id, drop the cache and re-read once (covers a resync that rotated the store).
- For each `Benefit`: if not in the manifest → verdict 1 (Not applicable, no call). Otherwise call `verifiedpermissions.is_authorized` with principal `Worker::"<caseId>"` and its attributes passed inline as entities, action `claim`, resource the benefit.
- Apply the verdict mapping in §6.2 and join `determiningPolicies[].policyId` against the policy map to produce `{benefitId, verdict, cited: [{id, source, confidence}]}`.
- Write the case to DynamoDB. Return results + `rulesetVersion` + `caseId`.

### 7.2 `explain` (Strands agent on Bedrock)
- Input (sent by the frontend, which has already evaluated `requirements.json` for the "why" list): `{results: [{benefitId, verdict, cited: [{id, source}], why: [{label, met, actual, required}], nextStep}], language}`. This is the only text the model sees; the "90" in "73 of 90 days" is therefore in the input, which is what the §10 guardrail relies on.
- System prompt constraint: *"You are given a decision and the exact rule text that produced it. Restate it in simple <language> for a delivery worker. Do not add rules, thresholds, or advice not present in the input. End with one next step from the provided `nextStep` field."* `nextStep` strings live in `requirements.json`, hand-written.
- Output is labelled in the UI as "Explanation (generated from the rule above)". The decision card never depends on this call; if Bedrock fails, the card still renders with the raw citation.
- Model: the cheapest Bedrock model that handles Hindi well; verified on day 3 with three sample outputs.

### 7.3 Frontend
- Single page: form (left), results (right). Mobile-first layout; the demo shows it on a phone-sized viewport at least once.
- Results: one card per benefit with a big verdict, the cited policy `@id` and `@source`, a "why" list (requirements met / not met), the explanation, and a language switch (EN/HI[/KN]).
- **Jurisdiction toggle** at the top; on toggle, re-POST and animate cards that changed. A "View rulebook" drawer shows the two `.cedar` files side by side with the determining policies highlighted.
- Persistent footer in the product, not a splash: *"HaqCheck shows which written rule applies to the facts you entered. It is an eligibility estimate with citations, not legal advice. Rules change; this rulebook is version <v>, published <date>."*

### 7.4 Stretch (day 4 only, only if §7.1–7.3 are demo-ready): rule-drafting assistant
- Paste rule text → Strands agent proposes a Cedar policy → the proposal is validated by attempting `CreatePolicy` on a **scratch** policy store with the shared schema (AVP has no dry-run; a validation error is the reject signal) or with the Cedar CLI locally → shown as a diff for a human to accept into the repo. Never auto-published. This is the "propose-then-verify" loop from the 2026 AutoCedar / autoformalization papers, but framed honestly: a drafting aid with human review.
- Demoed only if it works in rehearsal; otherwise mentioned in one sentence.

## 8. Data flow (happy path)

1. Worker fills the form; picks jurisdiction (defaults to their state → Karnataka if `KA`).
2. `POST /evaluate` → Lambda validates, resolves policy store, two `IsAuthorized` calls, DynamoDB write, returns results.
3. Frontend renders cards immediately from results (no LLM in this path).
4. Frontend calls `POST /explain` with results + language; the card shows a placeholder until the response arrives (a single response, not a stream).
5. Worker toggles jurisdiction → steps 2–4 repeat; changed cards animate; rulebook drawer highlights the new determining policies.

## 9. Error handling

- Invalid input → 400 with field-level messages; form shows them inline.
- AVP error or throttle → 502 with `{"error":"engine_unavailable"}`; UI shows "Rule engine unavailable, try again" and does **not** fall back to an LLM answer (this is a product principle and is stated in the README).
- Bedrock failure → explanation card shows "Explanation unavailable; the decision above is unaffected."
- DynamoDB write failure → log and still return results (the case log is not on the critical path).
- Ruleset lookup missing → 500; deploy script fails loudly if `RULESET#` items are absent.

## 10. Testing

- **Policy tests (the important ones):** `policies/tests/cases.json` holds ≥12 cases across the two rulebooks (every rulebook gets its own boundary cases): threshold boundaries (89/90/91 days), unregistered on e-Shram, non-KA state against KA fund, non-notified platform, and a benefit outside the manifest (vehicle-type cases only if a vehicle condition emerges from the primary sources). Each case asserts the verdict **and** the cited `@id`s. `run_tests.py` evaluates them against AVP via the same mapping code the Lambda uses, and first checks `ListPolicies` per store against the expected count so a half-failed sync is caught. Run after every policy sync.
- **Handler unit tests:** pytest with moto/stubs for the AVP → result mapping and input validation.
- **Explanation guardrail check:** three fixed inputs, assert the output contains no digits other than those present in the input (cheap hallucinated-threshold detector).
- **Demo rehearsal:** two scripted cases run end-to-end on the deployed URL on Saturday night and Sunday morning; screenshots of expected output kept as a backup slide.

## 13. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Rules are more complex than a few Cedar conditions | Day-1 go/no-go. Scope to the parts that *are* threshold/attribute checks; annotate the rest as `@confidence("simplified")` and say so in the UI. |
| Legal facts wrong or stale | Primary sources before Sept 17; `@source` on every policy; version + publish date in the footer; "estimate with citations, not legal advice" in the product. |
| A judge asks "how do I know the policy is what the court said?" | Answer: it is hand-authored and reviewed, with the clause quoted next to it; the LLM never wrote the shipped rulebook. Show the `.cedar` file. |
| A judge asks "show me a different case" | Case 2 is rehearsed; the form is live, so any inputs work. |
| Cedar learning curve | Learned pre-event on toy policies (allowed). AVP does the evaluation, so no local bindings are needed in production. |
| Bedrock latency or Hindi quality | Explanation is off the critical path; model chosen on day 3 from three samples. |
| Team is 1 person | Cut Kannada, cut the rulebook drawer, keep: form, two cards, toggle, EN/HI explanation, live URL. |
| AVP not available in the chosen region | Check on the pre-event list; fall back to `us-east-1` for AVP only. |

## 14. Fallback (only if the Day-1 go/no-go fails)

**ConsentLedger:** same Cedar-at-the-core mechanism applied to a shared document (rental agreement or hostel mess bill): the app extracts clauses, and Cedar policies decide which flatmate may view, approve, dispute, or pay each clause. Lower legal exposure, weaker urgency. Reuses the schema, AVP wiring, Lambda, and frontend shell from Day 1.

## 15. Decision record (LLM council, 2026-09-04)

Five advisors, anonymised peer review, chairman synthesis. Full transcript: `docs/superpowers/council/2026-09-04-haqcheck-council.md`.

- **Agreed:** Cedar is the right tool, not a gimmick (eligibility is attribute-based access control: "may this worker claim this benefit"). The differentiator is that the LLM never decides. Form input must be primary. Ship It, for a live URL and legible AWS-centrality.
- **Clashed:** whether the LLM-to-Cedar compilation is the product (Expansionist), a day-4 stretch (Executor), or theatre to cut (Outsider). Chairman ruling: the shipped rulebook is hand-authored; compilation is an honest, human-reviewed drafting aid demoed only if it works.
- **Clashed:** localisation as the star (Outsider) vs cut entirely (First Principles). Ruling: keep EN + HI as a cheap, off-critical-path Bedrock call; Kannada only if time.
- **Blind spots caught in review:** verify primary sources before the event; Cedar running locally is not legibly "AWS" to a judge, so use Amazon Verified Permissions; rehearse a second case; PII concern disappears once screenshots are cut; check Cedar learning curve pre-event.
- **Verdict:** REVISE → adopted as this spec. Fallback ConsentLedger kept as the Day-1 escape hatch only.
